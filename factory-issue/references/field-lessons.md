# factory-issue field lessons

No pending field lessons. New lessons may be appended by the post-skill field-lessons loop.

## 2026-10-21 — "unblock" a `factory:stuck` issue that already has a draft PR

The factory's stuck comment says "fix the cause, then set `factory:ready`", but `stuck → ready` starts a **new run from base**, on a branch the factory names itself: the existing PR's branch is never resumed, and the state table allows no hand-set `pr-open`. When the stuck reason is the review cap (work complete, PR green), re-readying throws the work away and usually hits the same cap. Read the PR first (`gh pr view N --json isDraft,mergeStateStatus,body`), review the unreviewed tail, and offer the owner: finish the PR by hand on its branch, or tighten the criteria and rebuild. Record findings as a PR review either way, so the next actor reads them where it looks.

## 2026-10-21 — a review on a hand-assembled PR reaches no factory

The `pr-open` feedback loop watches only the pull request the factory's own live run opened (the `pr_url` on the run record). A PR a person assembled from the factory's merged parts (#562 on tc-people, from an integration branch) has no run behind it, and the issues' `factory:pr-open` labels are stale once their own PRs merged or closed. Before promising "the factory will pick it up", check the run records on the watching Mac (`~/.config/t3fac/factory/runs/<owner>__<repo>__<issue>__N.jsonl`, last `state_changed`/`finished` event). If every run is finished, the choices are: fix by hand on the PR branch, or file new issues with `## Base: <pr branch>` so child PRs land into it. Re-readying the old issues starts a fresh build from base and discards the branch.

## 2026-10-21 — filing for a repo that does not exist yet, with sources in another org

Bootstrap before any body: create the repo, commit the spec and plan and a `.dw/config.yml` whose gate passes on an empty tree (an aggregating `Makefile` whose targets are no-ops until each side registers its own `make.mk`), create the seven labels one `gh label create` per line (a `for … set --` loop silently passed empty colours), clone to `~/t3fac/<owner>/<repo>` and `t3 project add` it. The factory claimed the first two issues within a minute of `ready`, so the registration is live without a restart. Check `GH_CONFIG_DIR=… gh repo view` for every repo the bodies tell the session to read: the factory login (rawphp) could not see the Trilogy-Care repos, so ported sources went into the new repo as a pinned `reference/` snapshot (SHA table in `reference/SOURCES.md`, secrets grepped and a test APP_KEY redacted first). Two parallel scaffold issues must not share a file: separate workflow files and per-side make fragments instead of one `ci.yml` and one `Makefile`.

## 2026-10-21 — needs-info over a missing `reference/` source: supply it, do not redesign

When the session stops because a file the issue says to copy is not in the snapshot, the answer is the file, not a fallback design. Find the pinned commit in `reference/SOURCES.md`, a local clone of the source repo (`find ~ -maxdepth 4 -type d -name '<repo>'`), and `git show "${SHA}:path"` it into the snapshot on `main`, then compare `md5` against the source before committing. Quote the braces: in zsh `$SHA:path` is parsed as a parameter modifier and `git show` prints the commit instead of the file; the first push here shipped four copies of a commit header. Also follow every import of the files the issue names (CSS `@import`, `@/…` aliases) and fold each one into the criteria, so the next run has no second gap.

## 2026-10-21 — "unblock" a stuck issue whose cause was the machine, not the branch

When the stuck reason is environmental (full disk, refused socket, slow gate) and the PR is green in CI, prove it before touching labels: run the repo's gate in the PR's own worktree. A fresh worktree has no `node_modules`, so run the side's provision target (`make provision-frontend`) first or the frontend step fails with `next: command not found` and looks like a code fault. Green gate plus green CI on the same head: `gh pr ready N`, comment on the issue that `factory:ready` would discard the branch, and hand the merge to the owner. Leave `factory:stuck` on; the `Closes #N` in the PR body clears it at merge.

## 2026-10-22 — filing an architecture audit's quick wins a day after the audit

An audit finding's CI evidence goes stale fast: the report's T-004 named preview-page a11y failures, but a PR merged the same evening fixed those and `main`'s latest run was red on a different surface (a `Skeleton` with `aria-label`). Before writing a CI-fix body, list the latest run's jobs on base (`gh run view <id> --json jobs`) and pull the failing test names and the offending `html` nodes from that job's log; file the body against what is red now and say so under `## Notes`. Also grep every env or config key a finding's "how to fix" names: `CHAT_PROVIDER` did not exist (the mock provider is chosen by key absence), so the criterion became "force the keys empty". Run `npm audit`/`composer audit` yourself before writing an "add an audit step" criterion, so the body says whether the step passes today and names the one package to bump.

## 2026-10-22 — needs-info on a screen issue whose criteria name reads the backend lacks

people-hub #23 bounced because two page criteria (past holders of a position, a cadence select) had no read or write behind them. Settle each from the spec's own rule, not by inventing: a detail-page read is a thin controller when the spec says screen reads are not capabilities, and a write with no capability in the spec's write table becomes display-only with a Notes line saying the capability would be its own issue. When the new route lands in a file an open PR also edits, read that PR's hunks (`gh pr diff N | awk '/^diff --git a\/<file>/,/^diff --git/'`) before adding its issue as a blocker: an append at the tail and an insert inside an existing group merge cleanly, and a blocker that is itself `factory:stuck` would stall the dependant for nothing. Say so under `## Notes` so the build does not ask.

## 2026-10-22 — a building sibling's Notes can name the issue you are unblocking as its dependant, unlinked

Unblocking people-hub #26, the ready/building list showed #69 (membership `roles` set) building, and #69's own `## Notes` said "#26 builds on this", yet #26 had no link to it. Also search main for a sibling domain that already solved the same question (here the 360's `Viewers` and `FeedbackAdmins` held the leaver, direct-leader and role lookups spec 6.3 asks of check-ins): reusing it answered three of six questions and removed a redesign.

## 2026-10-22 — needs-info because "run `npm audit fix`" cannot clear a bundled advisory

tc-supplier-portal-v2 #12 bounced: the criterion said `npm audit fix` (no `--force`) resolves the one high advisory, but the vulnerable package was bundled inside `aws-cdk-lib`, which npm cannot fix in place. The answer is the explicit change, not a relaxation: `npm view <pkg> version` to confirm the fixed release exists, then a criterion that names the exact version bump in `package.json` plus `npm install` and the suite that must still pass. Two cheap checks before any CI-step body: grep the real `name:` of the install step in every job you quote (one job here was "Install", not "Install Dependencies"), and `gh api repos/OWNER/ACTION/releases/latest --jq .tag_name` for each pinned action, because some (setup-php) tag without a `v`, so a "`# vX.Y.Z` comment" criterion is unmeetable as written. A local `npm audit` on a large lockfile can hang for minutes; do not block the unblock on it, scope the step out with a Notes line instead.

## 2026-10-22 — a gate step that joined main after the branch was built fails on the branch's own new code

tc-supplier-portal-v2 #13 (PR #31) was `stuck` on the time limit with every criterion ticked and the branch's CI green on everything the branch knew about; main had since added Larastan to the gate, and it flagged the branch's new class (a `final` class with an empty `const` allow-list makes PHPStan read the lookup as dead code). Before pushing the merge, diff the gate between the branch and main (`git diff origin/<branch>...origin/main -- .github/workflows source/backend/composer.json .dw`) and run every step that joined, not just the suites the PR body lists. For a red job that the PR does not touch, pull the failing test name from the job log and from the same job on main's adjacent runs (`gh run list --branch main --workflow <name>`, then `gh run view --job <id> --log | grep '1) Tests'`): the same test red on one main run and green on its neighbours is a flake to name in the PR comment, not chase.

## 2026-10-22 — trilogy-mac runs t3fac now; softfac's config is gone

The step-1 command for Trilogy-Care repos (`grep "repo:" ~/.config/softfac/config.yml` over ssh) fails: `~/.config/softfac` no longer exists on trilogy-mac. The watcher is t3fac: `ssh tomk@trilogy-mac 'cat ~/.config/t3fac/factory/config.yml'` lists `repos:` with each clone's `path` and `project_config` (`/Users/tomk/factory/Trilogy-Care/<repo>/.dw/config.yml`, which may exist only there, not in the local checkout); its `gh_config_dir` is `/Users/tomk/.config/t3fac/gh`, so the visibility and `workflow`-scope checks run over ssh with that prefix. Also for a CI-timing issue: a pull request's run executes the base branch's workflow (the `N/merge` ref), so read `git show origin/main:.github/workflows/build.yml` after a `git fetch`, not the local checkout or the PR branch, and take step times from a completed run's `gh run view <id> --json jobs` (`startedAt`/`completedAt` per step), since an in-progress run reports `0001-01-01` for unfinished steps.

## 2026-10-22 — needs-info because the criteria said "throw the exceptions the fake already throws" and the fake throws nothing

tc-supplier-portal-v2 #65 bounced on a premise the issue author assumed: `FakeAbrLookup` returns `null`, never throws, so "as the fake already does" named behaviour that did not exist, and the "callers need no change" line contradicted the only honest fix. ## 2026-10-24 — stuck on a transient 429 with a pushed branch but no PR: re-ready, do not hand-finish

people-hub #104 went `stuck` three times on the same "credentials cooling down" 429 with `gate_attempts: 0`; attempt 1 had pushed a complete commit to its session branch, and the owner's issue comments told "the next run" to resume it. Two things to know before touching labels: the next run never reads comments or old branches (it copies the body and starts from `base` on its own branch), so resume notes are dead text; and the cause is proven cleared by the factory's own later runs, not by waiting (`ls -t ~/.config/t3fac/factory/runs/ | head`, then the newest file's `finished` event: an `outcome: pr-open` after the 429s means the credentials recovered). With the work small, the gate unrun and the owner not asking to fix it here, the right move is one comment stating the cause cleared plus where attempt 1's branch sits, then the label swap as its own command. Hand-finishing is for the complete-and-green case (see 2026-10-21/22 lessons), not for a run the rate limit killed before the gate.

## 2026-10-25 — a new rule enforced by a test, with siblings still converting the old code
