# Editing a filed issue

Rules for changing an issue that already exists: answering `factory:needs-info`, rewriting, splitting, moving requirements. Changes at `factory:pr-open` and postponing are in the `SKILL.md` quick reference.

- **Keep the number.** An existing bug report becomes a factory issue in place: move the reporter's evidence into `## Outcome`, give the title its `<type>: ` prefix, add `factory:proposed` and the `type:<type>` label, then swap to `ready`. A needs-info issue rewritten to a new design keeps its thread, which records why the old route failed.
- **Re-check before answering.** Pull the default branch and re-check each question against it, because siblings merge between the ask and the answer. Check the factory's technical claim in the code (one grep) before answering it, and search base for a sibling domain that already answers the same question. Grep every open `ready` and `building` body for this issue's number (`gh issue list -R OWNER/REPO --state open --json number,body --jq '.[]|select(.body|test("#N\\b"))|.number'`): each hit is a blocker to link or a Notes line to write.
- **The brief and the code disagree:** read the spec section the issue cites and the plan line that built the code, and decide which is wrong. When the code is, file the fix as its own issue and block this one on it, with a Notes line on any sibling that renders the same thing.
- **Fold every answer into the body** as an instructor edit; the next run copies the body and may not read comments. Post a short numbered answers comment for people. Read the thread with `gh issue view N -R OWNER/REPO --json comments`.
- **After an answer that corrects a mechanism,** grep the open `ready` and `building` bodies for the wrong term and for any helper the answer introduces. Fix each wrong criterion with a minimal instructor edit, and chain every issue that needs the new helper behind the one that adds it, so parallel builds do not each add it.
- **A stop over a missing source file** the issue says to copy: the answer is the file, not a fallback design. `git show "${SHA}:path"` it from the pinned commit into the snapshot (quote the braces: zsh reads `$SHA:path` as a modifier and prints the commit), compare its checksum with the source, and fold every import of the named files into the criteria so the next run has no second gap.
- **A proposed split:** rewrite the original as one part, keeping its number and links, file the rest new, and make the answers comment point at each new issue.
- **Moving a requirement to a sibling:** check the sibling's label first (an edit to a `building` issue restarts its session's contract). Append one criterion there, its `## Depends on` line and link, and "Moved here from #N".
- **Before adding a dependency,** check that issue's own blockers. A chain onto external work stalls this issue; a field or column that already exists may need no new dependency.
- **The answer is a change in another repo:** check that repo is watched, then search its issues for the class or code you will name before filing (parallel sessions file the same fix). If duplicates exist, pick the one whose design fits every dependant and tell the user to close the other. Link it `blocked_by` across repos; the REST call takes the other repo's issue id.
- **A batch of needs-info issues:** one research agent per issue in parallel works. Ask each to list the sibling issues its answers touch, and add those cross-links before flipping anything to `ready`.
- **Notes that contradict the label** (a "Parked, do not mark ready" line on an issue the owner has marked ready): rewrite the line to say what the build does not need.
- **In auto mode,** write the whole edited body with the file tool and `gh issue edit --body-file` it; a scripted substitution that rewrites the body can be refused.
