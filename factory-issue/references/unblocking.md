# Unblocking a stuck issue

Rules for a `factory:stuck` issue, or a run that has finished while its pull request still needs work.

- **`factory:ready` starts over.** Moving `stuck` to `ready` starts a new run from base on a branch the factory names itself. It never resumes the old branch or its pull request, and nobody can hand-set `pr-open`. Read the pull request first: `gh pr view N -R OWNER/REPO --json isDraft,mergeStateStatus,body`.
- **Work complete, stuck on a cap** (review cap or time limit, pull request green): re-readying throws the work away and usually hits the same cap. Review the unreviewed tail and offer the owner two exits: finish the pull request by hand on its branch, or tighten the criteria and rebuild. Record findings as a PR review either way, since the next actor looks there.
- **Read the run record before promising "the factory will pick it up".** The `pr-open` feedback loop watches only the pull request its own live run opened. A pull request a person assembled from merged parts has no run behind it, and its issues' `pr-open` labels are stale. On the watching Mac, read the last `state_changed` or `finished` event in `~/.config/t3fac/factory/runs/<owner>__<repo>__<issue>__N.jsonl`. When every run has finished, the exits are a hand fix on the pull request's branch, or new issues with `## Base: <that branch>` so their pull requests land into it.
- **Stuck on the machine** (full disk, refused socket, slow gate) with the pull request green in CI: prove it before touching labels by running the repo's gate in the pull request's own worktree. A fresh worktree has no installed dependencies, so run the repo's provision step first, or the failure looks like a code fault. Green gate plus green CI on the same head: `gh pr ready N`, comment on the issue that `factory:ready` would discard the branch, and hand the merge to the owner. Swap `factory:stuck` for `factory:pr-open` (`gh issue edit N --remove-label factory:stuck --add-label factory:pr-open`): an issue whose pull request is ready for review is not stuck. The factory ignores a `pr-open` issue with no live run, so this starts nothing; `Closes #N` closes it at merge.
- **Hand-finishing a complete pull request:** first list the red job's conclusion on main's recent runs (`gh run view <id> --json jobs`), so a red that main shares is named as main's and not chased on the branch. A test red on one main run and green on its neighbours is a flake to name in the PR comment. Then `git worktree add --track -b <branch> .worktrees/prN origin/<branch>`, `git merge --no-ff origin/main`, and resolve by hand. Before pushing, diff the gate between branch and main (`git diff origin/<branch>...origin/main -- .github/workflows .dw` plus the tool configs) and run every step that joined since the branch was built, not only the suites the PR body lists. Then push, `gh pr ready N`, comment on the issue, swap `factory:stuck` for `factory:pr-open`, and remove the worktree.
- **Re-read the labels just before and just after commenting** (`gh api repos/O/R/issues/N/events`: labeled and unlabeled, with actor and time). If someone set `factory:ready` while you finished the pull request by hand, a fresh run from base now duplicates it. Report the collision and both exits to the owner, and do not pick one: merge the hand-finished pull request now and let the run die on the closed issue, or let the run finish and close the hand-finished one.
- **Stuck with no pull request and no remote branch** (`git ls-remote --heads origin` lacks the branch the stuck comment names): the run stopped before pushing and the factory removed its worktree, but the commits are still in the factory's clone. Read the run record's `finished` event (`gate_attempts`, `pr_url`), then from that clone `git log --oneline main..<branch>` and `git push origin <branch>`, over ssh for `trilogy-mac`. `gate_attempts: 0` means the gate never ran, so run the whole gate plus any step that has since joined main before finishing it by hand.
- **Stuck on a 429** ("credentials are cooling down"): siblings that went `stuck` in the same minute (`ls -t ~/.config/t3fac/factory/runs | head`) mean the cause is concurrency, not the issue. In one pass, check for salvage (`git ls-remote --heads origin`, `gh pr list`) and `git grep` `origin/main` for the premise the body states, since siblings merged in between. Write the cause in an issue comment and fold the resume note into `## Notes` as an instructor edit, then swap `stuck` for `ready` as its own command. Ready one of a stuck batch at a time, hours apart, or the same 429 recurs: retries minutes later die inside the account's usage window. Lowering `max_concurrent_runs` in the factory config also works, from the next pass. Proof the limit cleared is a later run's `finished` event with `outcome: pr-open`, not elapsed time. A run the 429 killed before its gate is re-readied even with a pushed branch; hand-finishing is for complete, green work.
