# Drafting the body

The session sees only the issue body and its own repo's checkout on `base`. Each check below closes a gap that sent a real issue to `factory:needs-info`.

## Ground the brief before the criteria

- **Reproduce a bug report** the way the user ran it. If it works, ask where they saw the failure. A failure only an app or a background job sees: rerun as it runs, `env -i HOME=$HOME PATH=/usr/bin:/bin <cmd> </dev/null`. Put the reproduction in `## Notes`. When the fix renames or repurposes a command a script calls, the script change is a criterion.
- **Measure a vague ops brief** (`du` the dirs, read recent status and log lines, grep the docs for what is already handled) before cutting it into issues.
- **Diff a design image** element by element against the code. Say in `## Outcome` what already matches and must stay, and in `## Notes` which image-only text stays off the screen.
- **Quote a CI failure from the job log of base's latest run** (`gh run view <id> -R OWNER/REPO --json jobs`, then `--log | rg -i "<term>"`), not from a comment or an audit report, whose evidence goes stale within a day. For an e2e flake, the passing retry overwrites the failed attempt's trace, but the blob report artifact (`gh run download <run> -n <blob artifact>`, unzip) keeps each failed attempt's `error-context.md`. Grep the leg's log across runs for `✘.*<spec>:<line>` to count failures and check they share one line and message. Blob artifacts may expire in a day, so quote the messages in the body.
- **"CI never runs test X" can mean the factory gate, not CI.** Read the CI workflow's DB and env for the test job and the `.dw` gate's env separately before writing the Outcome. A brief asking to quarantine flaky tests collides with the no-skip rule: the criterion is "make it deterministic, stop needs-info", with quarantine only after the owner's written yes.
- **Check every claim about existing code.** Trace each field a screen shows to the response type, each HTTP status a criterion names to the framework's exception mapping, each path to the conventions of the code that has landed, each env or config key a fix names to the code that reads it. Settle each mismatch in the criteria and name the settled choices in the report.
- **Grep every reader and writer on base before a criterion changes shared behaviour.** A brief names one caller; base has more, and each missed one is a gap the build finds mid-run. Check:
  - every caller of a rule you move, and every caller of a predicate you relax (it may gate other paths too);
  - what every caller passes before changing a default;
  - every shape that builds the object, not only `new X(`: named-argument constructors and raw readers of the column that do their own arithmetic;
  - every writer of a column a user-set flag would reuse, scheduled jobs included (a nightly sync undoes the user's setting);
  - every reader of a helper the issue retires, by import name;
  - every command that changes a provider's copy on purpose, before a design compares the local id with it;
  - the loader a read uses before wiring a rule into it, and the real strings a fixture only shapes;
  - tests that pin the old rule by name: work their numbers under the new rule and name any that change.
- **Before folding a council or reviewer verdict into a criterion,** open every file it names and check what that file actually maps. A nit about stale text may be stale only against the reviewed PR's head: read the PR's hunk for that file and drop it if the PR fixes it. A finding that a now-required field "breaks queued entries or older callers" needs the call path on every first-parent commit of base (`git log --first-parent -- <file>`), not only today's.
- **Narrowing a read** (paging, a window): check the screen that renders it is on base. If not, block on the screen's issue and put the "show older" criteria in this body.
- **Drafting a later piece of an umbrella spec:** read the earlier piece's own scope section first (it may defer items to this piece), and check whether the spec requires a per-piece build spec. If it does, that build spec is a no-label tracking issue every build issue blocks on.
- **Read the newest spec**, from the default branch on `origin`, not a stale local copy. Find designs a spec names but the repo lacks (grep `~/.claude/projects/<project>/*.jsonl` for the phrase and for `.html` paths). Quote copy from the mock's text instead of paraphrasing it, and check the mock's screens and buttons against the issues so none is unowned.
- **Read the repo's architecture tests and test bootstrap** (`tests/Arch` or equivalent: naming rules, pinned maps, import boundaries, what the seeders run) before writing criteria. For a spec someone else drafted, give a fresh reviewer the spec and the repo, not your conclusions, and ask for mismatches with `file:line` only; "confirmed against the code" in a draft is not proof.
- **A new gap can contradict a decision already on base** (a meeting confirms it, the domain doc decided otherwise). Grep the domain doc for the concept before drafting, quote the standing decision in `## Outcome` with how the new work sits beside it, and make reconciling that doc section a criterion.
- **A "doc contradicts code" finding:** decide which side is intended first. `git log -S"<the copy>"` finds the issue that wrote it; when its Notes say siblings still build that behaviour, fix the code, not the copy. An open sibling usually covers most of the finding: file only what it leaves out and block on it. Grep the tests for one that pins today's behaviour on purpose, and name it in the criteria so the build replaces it.
- **When the spec line is the error** (a contradiction with code on base, a stale path), add a criterion that fixes the spec and plan lines too, or the next issue citing that section bounces the same way.

## Put on base or in the body everything the session needs

- **A repo path in a criterion must be on base:** after `git fetch`, `git cat-file -e origin/<base>:<path>`, and read code with `git show origin/<base>:<path>`. Reading a file only proves it is on disk, and the local checkout can sit behind `origin`.
- **A spec, plan or mock not on base yet:** commit it beside the spec first, or open a no-label tracking issue, put `Closes #N` in the PR that adds it, and block every build issue on #N so they can all go `ready` now. A plan that will not be committed: paste its shared rules and out-of-scope list into every body's `## Notes`. A self-contained HTML mock under about 50 KB that lives only in a scratch folder can go in the body inside `<details>` with a four-backtick fence; say in `## Notes` which parts are staging (demo scripts, sample data, panels with no endpoint) so the build does not port them.
- **Evidence the session cannot reach** (a raw reply, a fixture, your scratchpad) goes into `## Notes`. Pin an open PR by head and base SHA, since its branch goes away on merge. Content from another repo: pin the source SHA and give the read command, `gh api "repos/O/R/contents/<path>?ref=<sha>" -H 'Accept: application/vnd.github.raw'`, plus "stop needs-info if unreadable". Check the factory login can read that repo (`GH_CONFIG_DIR=<dir> gh repo view O/R`); when it cannot, commit a pinned snapshot into this repo first (a `reference/` folder with a SHA table, secrets grepped out) and point the body there. A copy-a-template change gets a `diff` against the source at that SHA as its criterion.
- **Write cross-repo refs as `owner/repo#N`**; a bare `#N` links to this repo's issue. Keep them under `## Notes` unless they should block.
- **The code the issue changes must exist on the branch it builds from** (`factory.base`, or the `## Base` branch). `git grep` that branch for every class, capability, method or pattern a criterion treats as existing. Each miss is a sibling to add under `## Depends on` and link, or something this issue builds. When answering such a needs-info, prefer the dependency over a split unless the standalone half delivers the outcome alone.

## Criteria

- **Settle every open choice** before `ready`: a range to one value, rounding ties, which data rule each field takes. Give a worked example's inputs in the units the rule takes, and write the expected numbers.
- **A removal lists its consumers.** Before "delete X", grep every import and entry point of X, give each consumer its fate as a criterion (one owned by a building sibling keeps its contract untouched), and close with a grep that must print nothing. Before renaming or removing a demo name, check whether the same name is also a real record in the repo; anchor the grep to the files the change owns and list the real references to keep. Check every deletion against the spec's parked or postponed rows too: a hit is filed `factory:proposed` + `postponed`, not ready.
- **Seed derived data through the domain.** A seed criterion that names a column the domain recomputes (a flag, a counter, a snapshot) must say the seed writes through the domain's own write path, with a fixed clock, and which inputs make the rule fire. Read the recompute class first; a hand-written value is erased by the next write.
- **Keep each criterion buildable inside this issue.** Say where a named setting is stored. When its screen belongs to another issue, move the requirement there instead of splitting it.
- **Run every check command** on the current base and confirm the stated pre-change output. A criterion that says a fix command will clear something (an audit fix, an auto-upgrade) must be proven too; when it falls short, name the exact change instead. Anchor a grep to the lines the change touches, so comments do not match.
- **Size the work to `limits.minutes`** (default 180). Split a larger one, or write the split rule into the body.
- **Out of scope, ops after merge:** steps the build must not do (a production re-sync, an admin action in a third-party tool) go under that line in `## Notes`, or the session tries them or bounces.
- **Approvals the session cannot ask for:** when the build needs a browser, a dev server or computer use and the repo's `AGENTS.md` says ask first, get the maintainer's yes in the chat and write "The maintainer has approved …" in `## Notes`. Split the part that needs it into its own issue, blocked by the rest. A value only an owner can create (a client ID): park at `factory:proposed` with a "pending, stop needs-info if still pending" line, and fill it before `ready`.

## Splitting for parallel builds

- **Split a big spec by layer** (storage, endpoint, UI) with chained links. All go `ready` at once and only the bottom is claimable. Cut a test bullet that needs code from two layers in two, each half in the issue that builds its code.
- **A plan written as one PR** may not survive being cut into chained issues that each merge to base. Walk each chunk's merge on base: put each migration's data copy with the table it fills, keep old capabilities writing until the screen moves, remove fields only after their last reader. Check every entry point the scaffold stubs (each CLI command, the server start, the main loop) has an owning task, and give the composing task its own issue blocked by the modules it starts. Write the cut into the plan so every body can point at it.
- **Narrowing or splitting a filed issue:** `git grep` base for its number in tests, fixtures and plans, as the bare number too (`=> 86`, `": 86`), not only `#86`; the issue that takes an entry updates every test that pins it. When a verdict says a requirement "stays with #N", grep #N's body for it; if absent, report the gap.
- **Give shared files their own early issue** (a bootstrap with registration hooks, the schema, the shared UI system), so later issues add files instead of editing one. Fix shared names (routes, events, helpers) in the bodies so parallel issues agree.
- **Name the anchor for every shared-file touch** ("register the route directly after the `x` line"), a different one per issue, and read a `ready` or `building` sibling's grep criteria for that file, not only its hunks (a sibling that requires a grep to print nothing fails on your helper), and prefer a new file per issue (an invokable controller) over methods added to one shared class. Then chain only issues that must edit the same function or component. A frontend issue gets its backend twin's API contract in `## Notes`, so the two build side by side.
- **A rule a test enforces, with siblings converting the old code:** file the rule first as a small issue whose test carries an exemption list, each line naming the sibling that removes it (a prefix entry covers code in-flight issues still add). Make the test fail on a stale exemption, so each sibling deletes its own line. Every later issue then depends only on the rule issue.
- **Porting code:** pin the source SHA from `origin/main` (a local clone can be far behind), extract it with `git archive <sha> <dir> | tar -x -C <scratch>`, and list each ported file's imports across directories before cutting. A file that imports code a dependant issue owns means the cut is wrong: move the shared classes down into the lower issue, strike them from the dependant, and park the rest as a `factory:proposed` + `postponed` sibling once you have checked who consumes it.
- **Before adding a criterion, grep the sibling bodies for it**, and put it in the issue that already owns that file or row. Two issues writing one row build conflicting code.
- **Building on an open PR:** run `git merge-tree --write-tree --name-only origin/main <pr-branch>`. When it conflicts, the resolution can decide a signature this issue uses: word the criterion for both outcomes and say in Notes to read the merged code first.

## Special cases

- **Adds a `.github/workflows/` file:** check the factory login's token has the `workflow` scope (`GH_CONFIG_DIR=<dir> gh auth status`), every secret it reads is visible (`gh secret list -R OWNER/REPO`, `gh api repos/O/R/actions/organization-secrets`), and a private action grants access (`actions/permissions/access`). State each result in `## Notes`.
- **Makes a new status or check appear on PRs:** check whether the base branch requires it (`gh api repos/O/R/rules/branches/main --jq '.[] | select(.type=="required_status_checks")'`; no output means none) and say so in `## Notes`.
- **An issue a bot keeps updated:** a rename by a non-instructor after `ready` stops the build as stuck. Check the workflow's schedule against the build time, and refresh the body from the bot's latest comment as an instructor, since the session reads the body, not the comments.
