# Fixing: what comes back next round

Read before the first fix. Each rule here cost at least one saved round. SKILL.md's Fix table says what a fix is; this file says which findings are not yours, what makes a fix the next round's finding, the check before a coverage commit, and what to do when the branch moves under you.

## Not yours to fix

- **Out of the diff.** A finding on a file `git diff --stat <remote>/<base>...HEAD` does not touch came in with a merge of the base. It escalates each round and stalls the stop rule. The person settles it ("already on the base") or raises it against the base; ask before the next round. First ask whether the base was wrong without the PR: a help line, a copy or a doc that only this change made false is the PR's to fix in the same round, though the file is not in the diff.
- **A scenario the base already has.** A finding can keep its id and bring a new scenario each round. At each re-scope, check whether the new scenario reproduces on `<remote>/<base>` (read the base's code path, or run the test there). If it does, that part is the person's to settle as "pre-existing on the base", with the follow-up it needs; fix only the part the diff causes.
- **Pinned by the spec.** When the issue's acceptance criteria, a reference implementation (a port) or a "copied as is" rule pins the behaviour the finding objects to, the fix breaks the criteria. In a port, map every open finding to the reference test or doc sentence that pins it before fixing any: `grep` the reference's tests, then its docs. A sentence that states the behaviour pins it; a sentence the reference's own code contradicts is the one bug worth deviating for. A criterion that names a file ("a helper in copy.ts") pins the behaviour, not the location, unless it says the location matters. A settle listed in the PR body (a factory's own review) is not a review-gate settle: expect round 1 to raise it again, and list the body lines a fix makes stale. When every open finding is pinned, commit nothing, run no round, and ask the person with options per finding: the reference's position, the test, the cost, a recommendation. What the reference assigns to a later issue is that issue's scope. A finding can be half pinned (paging that must still count every row for a required total): split it at round 1, fix the half you own, and take the pinned half to the person with the criterion as the reason in the same round. A finding on a copied file is fixed in the source repo (own worktree, failing test, PR there), then re-pinned and re-copied; the PR under review waits.
- **A contract a sibling PR owns.** When the issue says the other half (the API, the UI) is built in parallel in PR #N, read `git diff <remote>/<base>...<remote>/<sibling branch>` (its docs and handlers) before fixing any contract finding. Premises it falsifies are settles that cite the sibling's line; what is left is real fixes or deploy order. Before re-applying a settle that cites a sibling, `gh pr view <N> --json state` it and look for a replacement PR. Once the sibling merges, merge the base and let the next round mark those findings fixed, which reaches the PR comment where a local settle does not. While the sibling is unmerged, run the e2e that needs it before each push on a throwaway merge: one script that adds a detached worktree, merges the sibling's branch, copies your uncommitted files over, provisions, runs the spec and removes the worktree.
- **A trade-off.** A finding whose fix picks between costs is the person's call: what happens when a dependency fails (degrade, abort, partial write); how many inputs an identity covers (a version, a cache key, an artifact name); what one signal must show to corroborate another; what a status field promises; which system owns a cleanup; what a storage layer guarantees; which side ships first across a deploy (a new enum value that clients loaded before the deploy cannot read: add the fallback, but it never covers those clients). Each pick the loop makes, the reviewers falsify from the other side, one round each. At the first such finding, write the options and their costs for the person instead of spending a round. Describe each option by what each consumer gets (for a commit status: what a repo that requires the check gets, and whether the author can clear it), and put every dependent decision in the same message (a privilege split: every input the privileged side will take unverified). So is a fix that makes a safety guard fail open on a transient condition, a lock timeout (a polling bound is unfair under load; bounding on no progress is fair, and so is unbounded-and-documented), a stale-resource fix that names only the success path (ask about the failure branch in the same question), and a probe-style fix that reads one error kind as final (put the error contract in the question: which answers are decisive, which are retried, and whether the caller can tell them apart). Where a structural answer exists, offer it first: order rules by trust and leave the untrusted match out of the record; when one mechanism draws a third angle, make the state immutable (one record per event, never rewritten) so nothing needs a lock or a re-read; store the truth and gate only the side effect, rather than holding stored state below its computed value; reorder save-then-undo around a slow call to check first, call, save last; clear on the owner's deletion event rather than on reading the thing's state; bound a health read by the run's own durable records rather than "now minus a window"; a port's reference answers its own failure modes.
- **A doc note or a fallback is not a fix.** When a fix text offers "or document it" and the behaviour change would reverse an acceptance criterion or widen the issue's contract, the note costs a round and the finding comes back. Take the scope question to the person at round 1 and run the round only for findings you own. A nit is no different: a note that clears the "note it, or derive it" half comes back promoted. When the structural half needs new storage (a column, a table), ask at round 1 instead of writing the note. A fallback is the same: when the structural fix a finding asks for (per-tenant credentials, a schema split) is what the contract defers, its "or, if that waits" half (a runtime guard, a token scan) buys one more rewording and a promotion. Fix the other findings, leave that one open with the contract line as the reason, and take it to the person at the round it first appears.
- **Out-of-scope paths.** Before a fix that moves or shares code across folders (a duplicated-component finding), grep the issue and the PR body for paths they put out of scope ("Do not edit", "out:"); check the sibling that owns them (merged means the reason is gone) and ask at the round the finding first appears. An out-of-scope note does not cover a stale claim on a line the PR itself edited: that one is the PR's, so offer the ready fix as option (a).
- **A factory leftover that calls a gap pre-existing** ("shared by the sibling routes") can be false. Grep the tests for the sibling pattern it names before passing it on as a settle, and give the person the result with a ready, mutation-checked fix as option (a).
- **A spec conflict.** A finding asking for the opposite of a criterion the issue and the PR body state: ask before the round, or when running unattended say in the report that it will come back promoted. If the person's answer covers fixing it, name the overturned criterion and the stale body line in the hand-over; the body is theirs.
- **A date called the future.** The reviewers' clock is UTC, so a date written in the morning east of UTC reads as a day that has not happened. Rewriting it makes the doc wrong for its readers: leave it open for the person to settle, with the commit's local timestamp (`git log -1 --format=%ad`) as the reason.
- **A claim about history.** "The Action posted this before", "an earlier release wrote this": a blind reader sees only the diff. Probe (`gh api repos/<o/n>/commits/<sha>/status`, `git grep <text> <remote>/<base>`) and, when nothing ever did, leave the finding open with those facts as the reason instead of keeping dead config.

## What makes a fix next round's finding

- **A finding on one of a set.** One hand-built button, one issue in a decisions list, one of six identical wiring sites: fixing one makes the siblings the odd ones out, or reads as the rest ignored whatever the fix text said about "or". Grep for every sibling and fix all in the same round, or say before the round which siblings you leave and why (a test there would only assert wiring; the issue is still open), so the person can settle those sites.
- **A doc inventory or a stale reference is a set too.** A `stale-doc-reference` on files the PR deletes covers every identifier they exported, not only their basenames: pull every backticked identifier out of the doc and mark each row whose identifier lives only in a deleted file (`git grep -w <id> <remote>/<base> -- <deleted paths>`), in every copy of the doc. A "the list still leaves out X" finding closes only when the same commit fixes every sentence that summarises or apologises for the old list. When a finding names one wrapper around a guarded call, scan for every method that invokes a callable inside it (a token scan, not a grep for the call), and put the full list in the first question.
- **Every state of the input.** A finding that one case of a state-to-message mapping is wrong: write one test row per state the mapping reads before committing, not only the named one. A finding that one call path holds a lock across a slow call: grep the module for every `lock()` and every public function taking the locked type, and fix them all with their tests in one commit (a cheap red test probes `try_lock()` from a callback the code already takes).
- **A fact or phrase the fix changes.** Before a fix or doc says behaviour follows a trigger (a config reload, a repair command), grep for what calls it at run time, and run any repair hint a new check prints against the new state. Before a message tells the reader to do something, grep for the route or UI that does it. When a fix corrects a fact or rewords or removes a phrase, grep for every other sentence that carries it: every file `git diff --name-only <remote>/<base>...HEAD` lists, tests included, plus the pages the diff links to. Fix them all in one commit. A hand-picked folder list misses one, and each miss costs a round.
- **A PR body line the fix overturns.** A fix that overturns a body line (a deploy note, a risk paragraph, a settle the factory listed in the body) keeps the finding open while the round reads the old `--body`. Pass a corrected copy as `--body` for local rounds, and ask the person to approve the body edit before the push so the Action's run on the pushed head reads the new body; editing the body alone starts no run.
- **Reproduced commands in a doc.** A finding asking for evidence is closed by reproducing it, and reviewers re-run the recipe exactly as written: write the server start with every flag used, each command verbatim, each table cell as the command prints it.
- **A fix half declined.** When the person declines one half of a fix text, fix the half you own and write the declined half and its reason into the commit message; the next round reads it and marks the finding fixed.
- **A marker the reader never sees.** An HTML comment or a hidden note that flags stale content does not clear the finding: readers of the rendered page still see the stale thing. When you cannot redo it this round (a screenshot you cannot retake), remove it in the same commit as the text fix, leave the comment for whoever redoes it, and list the redo as a follow-up.
- **A visual bound.** A fix that caps, clamps or truncates UI text is measured, not estimated: render the finding's own motivating string with the real stylesheet in a browser (a local page over http; Playwright refuses `file:`), count what fits, and write that measured claim where the fix explains itself.
- **An exact-list guard.** When the PR adds or tightens a test that pins an exact set (routes with a middleware, an allowlist, a catalogue), a sibling PR that adds one entry breaks it with no textual conflict. List the open PRs that touch the guarded files (`gh pr view <n> --json files`), trial-merge each and run the guard, and name in the report the one-line pin whichever merges second needs.
- **An edge you saw and left.** When a fix touches a call whose failure the surrounding code never handled, handle it in the same round; it is the same bug class, not scope creep. Name the edge in the commit message.
- **A comment the fix makes false, or one that points nowhere.** A behaviour fix makes the docblocks that describe the old rule false: grep the class and config comments for the method or rule you changed and reword them in the same commit. Before committing a comment a fix adds that names a file or script, `git ls-files <path>` it, or name a file the diff touches.
- **A collaborator the tests mock away.** A fix that works because of another module's behaviour (an interceptor, a middleware, a cache) needs one test that runs the real module with only the wire mocked, for the happy path and the failure it handles. Mocking the collaborator again proves nothing about the fix.
- **A finding that names a call site.** Untested caller wiring closes with a render or call test of that caller, with only its data hooks mocked. Moving the logic into the callee and unit-testing that leaves the caller's next edit green, and the finding returns as "no test renders the caller".
- **A gate has two sides.** Before gating a route, grep every caller of its URL: a fetch through the API client carries the token; `<img>`, `<a download>` and `window.open` do not. Fix both sides in one round, one test each, and name the callers in the commit.
- **Gate on what the guard resolved.** When a guard normalises input (`path.resolve`), return the normalised facts from it and gate on those, not on the raw request; test `./x`, `x//y` and `x/./y` alongside the plain form.
- **A race has two orders.** A deadline or any first-wins guard needs a test per order (the guard lands first; the other side ends first and the guard then does nothing), and its budget comes from grepping the callee for every limit it applies. Do not promise in docs that one side always wins.
- **A refusal has a transition side.** Before adding a refusal to a transition, grep every caller of that transition: a guard that closes one finding breaks the caller nobody named (a client's link that calls the same move). A fix that makes X refuse use while in state S makes the move into S the next finding. In the same commit, make that transition refuse or undo every place X is in use (grep the pivot and edge tables for X's id), and test the race both ways: the use committed after the transition's snapshot, and the transition after the use's.
- **A new column is a migration and a deploy-order question.** Nullable, backfill with a non-null fallback, constrain, drop, with a seeded migration test, in the first round. Write the new key only when it holds a value, and at the first deploy-order finding ask the person: migrate first and settle, or a runtime fallback. Do not write schema detection on your own; a cached guard draws two more findings.
- **A test-only privilege has two edges.** When tests arrange data under a context production never has, reset it at the harness's request boundary and restore it after the request, in one round, with a test per edge.
- **A helper unified to fix a nit.** Check every caller's use of the exact edge the nit names (a clamp, a seed) before pointing one at the other; if they differ, make the shared helper the pure one and move the clamp to the caller that needs it.
- **CI's static steps, refactorers included.** Before rewriting code only to get past a finding a reviewer got wrong, run every static step CI runs on the touched files (Rector, not only the formatter and analyser): a refactor rule can turn your rewrite back into the flagged form. When the gate requires that form, keep it, add one comment saying why it is safe, and show with a mutation check that the test fails without it. A library guard the reviewer cannot see is settled on its re-raise with the package version, the library file:line and the mutation result. When a fix deletes code a static-analysis baseline pins, run the full-project analysis (a partial run misses `ignore.unmatched`) and drop the entry; when a fix only changes how an inferred type is spelled, update that entry's message and say so. A formatter can rewrite an untouched line when you add an import: check every changed line in `git diff <base>...HEAD -- <file>` is yours. A comment fix in a file a generator reads (API resources, request rules) can change a generated file: run the generator check before the push. Run the issue's closing checks (`git grep … prints nothing`) on every fix commit.
- **A call-count finding.** Before fixing "called N times per pass and again per claim", read the guard at each claimed site; fix only the hot path.
- **An external CLI's error shapes.** When rounds keep finding wordings an error classifier misses, read that CLI's source at the installed version for every wrapper around the error before writing the fix.
- **Behaviour that differs by build profile or schedule.** A fix that adds an awaited step to a background task can turn a timing test red only under load: grep the tests for waits on that task's first observable call and run them beside a second suite. A fix that makes behaviour depend on the build profile turns tests that relied on the old path into live side effects in the other profile (a real keychain write): route those tests past the switch before running the other profile, and check the real store after.
- **A fork that silences fakes.** Moving side work into a detached fiber or task silences every test that relied on a fake throwing on an unexpected call. Add a test that records the calls and asserts none, in the same commit.
- **A new import across folders.** A fix that imports a constant, helper or component from another feature or layer is judged by the repo-wide boundary or architecture test, which names no file the fix touches. Run the full suite before the push, not only the touched tests and the basename grep. A finding that asks to move a file into folder X goes through the same test: read X's rule first, and when it forbids the move, take the nearest legal home and name the rule in a comment.
- **Records the old version wrote.** A fix that changes how stored records (ledger lines, rows, files) are read comes back for the records the deployed version already wrote. List the ones still in flight before the round, and prefer a fallback a reader can check (the old source first, the new one only when it is absent) over a version marker. A fallible read moved after an irreversible step (an archive, a delete) cannot count on the retry taking the same exit: check what the retry sees, or make the read non-fatal.
- **A wider read to filter on the client.** When a fix needs more states from a filtered endpoint, request each wanted state (or add a server-side filter), never `all`: the unbounded read is next round's finding even when the PR forbids backend changes.
- **A memo for a per-request cost.** Before fixing a "computed on every request" nit, check the runtime model (a long-lived worker such as Octane, or a fresh process per request under PHP-FPM or serverless). With a fresh process, an in-process memo never hits: leave the nit or use the shared cache, and never claim a saving the deployment cannot deliver.
- **A step the caller skips.** When several findings land on one step of a ported pass, compare the caller sequence with the reference's before fixing them one by one; a skipped step the reference runs first often explains all of them, and the per-finding fixes would break the ported tests.
- **A signal the fix text names.** Before building on an API field, scope or event the fix text names, run one read-only probe (counts only, no PII) and design around what it returns. The token may lack the scope, the plan may lack the feature, the test environment may never fire the trigger.

## Before committing a coverage test

- For each guard the test pins, remove that guard alone, run the file, confirm the new row fails, restore. A shared helper that rejects the same input, or a layer below that applies the same rule, leaves the row green with the guard gone: grep one layer down, then pin the guard with a unit test of the class that owns the finding's line and keep the feature test for the behaviour. Delete each conjunct of a new `&&` in turn: short-circuits hide the later checks, and a conjunct no test reaches is next round's finding. Ten seconds per row saves a round.
- Restore from backup copies (`cp` aside, mutate, `cp` back, `diff -q`) or commit the fix first. `git checkout -- <file>` restores the last commit and wipes the round's uncommitted fixes. Name each backup by its path (`sessions_mod.rs`): `cp a/mod.rs b/mod.rs <dir>/` keeps only the last of each basename.
- Make one mutant at a time: `diff` the backup against the mutant and see exactly one changed line (a `sed` can hit a same-named local elsewhere). Count it killed only when the targeted assertion fails, not an error from elsewhere. Run each under a cap (`timeout 60`, or `--testTimeout=800` for a promise chain): a mutant can hang the run instead of failing it, so restore the file first when one does. Mutation-check against the previous head's file (`git show <old>:<path>`).
- Vacuous passes the mutation check exposes: a "nothing was sent" assertion with no recipient in the fixture (create one and assert `assertNotSentTo`); a negated multi-value matcher (Pest's `not->toContain($a, $b)` passes when any one is absent: assert the exact list); a failure-injection hook that fires on another query than the target (match the target query's SQL); a stricter shared test double that makes tests writing under a placeholder key read nothing (write them under the real key and add a positive control); module-level state one test sets and later tests inherit (reset it in `afterEach`); a query-count test on a cached flag read (use the real store and flush before each measured request).
- In a trial merge, run tests with the gate's own runner flags: a serial run of a parallel-gated suite shares one database with other sessions and fails untouched files.
- A red check that comes back all green is broken until one swapped file provably differs (zsh does not word-split an unquoted `$files`, so a loop over it runs once).
- When the fix text names a production trigger (a window `error` event, a handler loaded from a CDN), run a throwaway probe that fires it in the test environment and records what was sent. If nothing is, test through the API the trigger calls, say so in a comment, and mutation-check the gate.

## The branch moves under you

- **Someone else pushed.** `git fetch <remote> <pr-branch>` before each round's commit and before the push, and read `gh pr view --json state` right before resolving a divergence: another session may already have merged the PR. If it moved, never force-push. `git diff --stat HEAD <remote>/<pr-branch>` empty means the same resolution (two sessions merged the base alike): move your unpushed branch to origin's commit. Otherwise report the two versions, then on the person's word merge origin in, keep the stronger guard per hunk, re-read `pr-state` (its head is now origin's) and run one round with that `--state-file`. Resolve per hunk. Never resolve a conflicted file with whole-file `git checkout --ours/--theirs`: it drops the other side's non-conflicting hunks too, including everything a base merge on that side brought in. Or rebuild from the other side's version and re-apply only your edits, then check `git diff <their head> HEAD -- <file>` for removed lines you did not write. Resolving by script: read each file before opening it for write.
- **The base moved.** A fix on a shared component or a generated catalogue conflicts as soon as the base changes the same file, and GitHub runs no workflow on a conflicting PR. After the fix commit and before the push, `git fetch <remote> <base>` and `git merge-tree --write-tree <remote>/<base> HEAD`. On a conflict: merge the base in, resolve (take the base's generator, re-add the entry, regenerate; a hunk that places a guard taking a row lock keeps the base's lock order, so grep the base for the other lockers of both rows first), run the whole gate on the merged tree before committing (a count or list the base added elsewhere is carried over without a conflict and only the gate sees it), say in the commit which files beyond the conflicts changed (when the base changed a function your fix works around, grep the fix for its calls and delete the workaround the base now covers), push, and run the next round with `--full`. Expect that round to carry the base's commits as findings for the person; name them as out of the diff. With no conflict, decide from a trial merge, not file names: `git merge --no-commit --no-ff <remote>/<base>`, run the PR's tests and the base's new ones, `git merge --abort`. A generated-file check that reads `git status --porcelain` always fails inside a trial merge: run the generator and judge by `git diff --stat -- <generated files>`. After every base merge, read the base's new commits for fixes to helpers or conventions the PR copied (a forked test racer, a migration-test form) and port them; grep each fix for constants or assumptions it took from code the merge touched (a cap borrowed from a list that just gained paging) and re-test that edge. On an add/add conflict with a sibling that landed the same script, diff the base's copy against the open findings first: the PR may shrink to the delta, which is the person's call. Green means no merge: merge only on a conflict or a code-level overlap, never because both sides touch one busy file (a doc gaining other rows). A merge you do not need costs a push, a CI cycle and a `--full` round, and a `done` stands.
- **The PR merged or closed.** Read `state` with `headRefOid` at setup and before each round and the push. Once merged, its head is frozen and `gh pr view` keeps returning it; stop rounds on the branch, put the fix commits on a new branch cut from them, push that, and hand over the compare URL. `git fetch <remote> <base>` before deciding how it merged: a stale base makes a merge-commit merge look like a squash. Kill any gate started on the old tree by its log path. When it merged with a merge commit and nothing is committed yet, fast-forward the loop branch onto the new base tip, rename it (`fix/<N>-review`), move `<common dir>/review/<old>.json` to the new key, and run the next round with `--base <remote>/<base>` and no `--pr`: it reads only the fixes. Opening the follow-up PR, naming the old PR's finding ids, is the person's call unless they asked for it.
